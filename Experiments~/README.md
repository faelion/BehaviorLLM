# Experiments

The measurements quoted in the package README, with the scripts and inputs that produced them.
The folder name ends in `~` so Unity never imports it; delete it freely, or use
`BehaviorLLM > Readme` to remove it together with the samples.

## The offline matrix

`run_matrix.py` drives a local `llama-server` over sixteen labelled guard situations, each paired
with the action a designer marked as correct, under twelve configurations: three models, with
structured output on and off, in each of the two decision profiles. 192 decisions in total.

The prompts and schemas it sends were generated by the package's own `PromptBuilder` and
`ActionSchemaBuilder` (see `gen_artifacts.cs`, which was run from a Unity Editor script), so the
harness benchmarks those saved fixtures. It uses its own Python HTTP and parsing code;
it does not execute Unity transport, observation collection, cancellation or dispatch.
Root-level fixtures and CSVs preserve the historical September baseline:

| File | What it is |
|---|---|
| `system_reactive.txt`, `system_deliberative.txt` | the cached half of the prompt for each profile |
| `system_dynamic.txt` | the same, with the per-turn action-availability contract enabled |
| `schema_reactive.json`, `schema_deliberative.json` | the JSON Schema applied during generation |
| `schema_gated_hurt.json`, `schema_gated_quiet.json` | schemas with an action withheld, for `run_gated.py` |
| `matrix_results.csv` | one row per configuration: validity, expected-action rate, latency mean / p50 / p95, cache hit rate |
| `matrix_decisions.csv` | one row per decision: raw reply, parsed action, whether it matched the label, latency |

`run_ablation.py` re-runs the situations with the designer's guidance reordered (exception first).
`run_gated.py` re-runs the six conditional-rule situations with the wrong action removed from the
schema instead of discouraged in prose.

## Reproduction

Install a llama-server through **Model Manager > Server**, or use an existing executable.
Download the three GGUF filenames listed in `run_matrix.py`. Python needs only its standard library.
From this folder, run:

```powershell
python run_matrix.py --server C:/tools/llama-server.exe --model-dir D:/models --output-dir runs/my-matrix
python run_ablation.py --server C:/tools/llama-server.exe --model-dir D:/models --output-dir runs/my-ablation
python run_gated.py --server C:/tools/llama-server.exe --model-dir D:/models --output-dir runs/my-gated
python run_coldwarm.py --server C:/tools/llama-server.exe --model-dir D:/models --output-dir runs/my-coldwarm
```

`--server` defaults to `LLAMA_SERVER` or the executable on PATH; `--model-dir` defaults to
`BEHAVIORLLM_MODEL_DIR` or `models`. `--port` defaults to 8090 and must be free. All scripts
accept `--input-dir`; omitted, they replay the historical fixtures next to the script.
Outputs default to a timestamped `runs/` directory. Use a different output directory for each
protocol to retain its metadata. Results include fixture SHA-256 hashes, repository commit and
dirty status, backend version, model filenames and sizes. Matrix replies are no longer truncated.

To test **current code**, regenerate inputs using the running Editor:

```powershell
unity command --project-path D:/MyUnityProject eval_file --file D:/path/to/Experiments~/gen_artifacts.cs
unity command --project-path D:/MyUnityProject eval_file --file D:/path/to/Experiments~/gen_gated.cs
```

The generators write to `<Unity project>/Logs/BehaviorLLMExperiments/`. Pass that directory
as `--input-dir` to each Python command. Keep the original fixtures intact. In the TFG development
tree, synchronize scripts and dated results between `Docs/Experiments/` and this directory.

`run_ablation.py` writes `ablation_results.csv`; `run_gated.py` writes `gated_decisions.csv`.
`run_coldwarm.py` records the first and second identical Reactive/schema-enabled request after
starting a fresh server for each model, excluding server startup. This explicit protocol does
not reconstruct the historical 1,956/112 ms illustration, whose original raw capture is absent.

The September 20 matrix retained 192/192 valid actions, but some expected-action rates and
larger-model latencies changed. See `runs/2026-09-20/` and its comparison notes. The gated run
matched 4/6 expected actions on Qwen 2B and 6/6 on Qwen 4B; a legal action is not necessarily
the designer's expected choice. These dated runs are regression evidence, not replacements for
the original thesis study.

## The live runs

`telemetry/` holds three runs recorded by the package's `DecisionTelemetryRecorder`, one JSON record
per decision plus a per-run summary row in `runs_summary.csv`:

| Run | What it measures |
|---|---|
| `20260910_150511_stealthguard` | StealthGuard, three guards on Granite 4.1-3B, four and a half minutes: 306 decisions, 77% of prompt tokens served from the cache |
| `20260909_191742_argsinline` | PrisonYard, eight characters on Granite 4.1-3B, five minutes, world-dependent argument values printed **in the action menu** |
| `20260909_192323_argsinstate` | the same scene, same build, same disturbances, with those values printed **in the state block** (the package default) |

The last two differ in exactly one setting, `dynamicArgumentsInState` on the decision
configuration asset, and are the source of the prefix-reuse comparison in the README (0.547 against
0.710 cache reuse, 2,250 against 1,686 ms median).

Each `*_decisions.jsonl` line carries the source id, timestamp, latency, prompt and cached token
counts, the action chosen and how the decision ended; each `*_sources.csv` summarises one character.
